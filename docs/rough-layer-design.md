# ラフレイヤー 設計・要件

作成日: 2026-08-09
ステータス: 要件定義／基本設計（未実装）
関連: [concept.md](../concept.md) 2.5 / 2.9 / 2.10 / 2.11

## 1. 目的

人間の頭の中にある**配置のイメージ**を、構造を確定させないままagentに渡すためのチャネル。

現状、人間からagentへの入力はテキスト1本しかない。テキストは「何を言うか」は運べるが、「左右の幅の比率」「下の帯が全体の何割か」といった**配置**は運べない。一方、ブロックを直接置く操作は配置を表現できるが、置いた瞬間にタグ・入れ子・クラスの決定を人間に強いる。ラフレイヤーはその中間、**位置と大きさとラベルだけを、矛盾したまま置ける場所**を作る。

タグ・入れ子・クラスの決定はagentの仕事とする。これは 2.11 で「flexの軸を人間に考えさせないのはツールの仕事」と決めた線を、キャンバスの外まで延ばしたものにあたる。

### スコープ

- 空スライドから構成を組む場面（0→1）

### 非スコープ

- 既存スライドの手直し（選択＋一言の領分。ラフは差分を表現できない）
- 内容が主で配置は任せたい指示（テキストの方が速い）
- 描画ツールとしての作り込み（色・線種・自由曲線は持たない）

## 2. 要件

| # | 要件 |
|---|---|
| R1 | ラフモードへ1操作で出入りできる。モード中であることが画面から明らかである |
| R2 | ドラッグで矩形を描ける。描き終わった直後にラベルを入力できる |
| R3 | 矩形を移動・リサイズ・削除できる。それ以外の編集手段は持たない |
| R4 | ラフをagentに渡せる。添えるテキストは**任意**（ラフ単体で指示として成立する） |
| R5 | 生成結果の上にラフを重ねて表示し、ズレを目視できる。表示はトグルできる |
| R6 | ラフが消えるタイミングが予測可能で、明示的な後始末を要求しない |

R5 はこの機能の中心である。矩形を描く部分だけを作って照合を作らないと、単に遠回りな指示入力になる。

## 3. 設計判断

### D1: ラフはHTMLの真実に混ぜない

`slides/*.html` にも `.weave/deck.json` にも書かない。保存対象外、git対象外、**undo対象外**。

undoから外す理由は、undoの実体がHTMLスナップショットだから（2.10）。ラフはHTMLではないので、混ぜるとundo1回の意味が二重になる。ラフの描き間違いは Delete で消す。

### D2: 表現は1280×720座標の矩形＋ラベル

```
{ id: string, x: number, y: number, w: number, h: number, label: string }[]
```

agentには画像を送らず、このJSONを送る。2.9で設計サイズを1280×720に固定し絶対pxで書くと決めているため、**ラフの座標系はagentがCSSを書く座標系とそのまま同一**になる。ビジョンモデルへの依存が要らないのはこの決定の副産物であり、可変ビューポート前提のツールでは同じ形が取れない。

ラベルは中身の指示としてそのまま使う。粒度＝確定度の素直な対応にする（「Q3の要点 3つ」→3項目のプレースホルダ／「前年比 118%」→その数字が入る）。

### D3: ラフは近似であり、絶対配置で再現させない

**最大の落とし穴。** 座標を渡すと、agentは座標を忠実に再現しようとして絶対配置CSSを書きうる。これは 2.10 で「宣言的フローを選ぶ核心理由はagentにとって寛容だから」と決めた方針と正面衝突する。

したがってプロンプトで明示する:

- ラフは**比率と順序の近似**であって、座標の指定ではない
- 出力は Row / Column / Grid のフロー構造であること
- 揃っていない・重なっている矩形を整えるのはagentの仕事であること

### D4: テキストなしで送信できる

R4 の帰結として、送信の必須条件は「テキスト**または**ラフ」になる。現在は `server/local-api.mjs` の `requireText(payload.prompt)` がプロンプト空を無条件に弾くので、ここの契約を変える必要がある。

クライアント側で既定文を埋めて回避する案は採らない。指示の出所が人間なのかツールなのか曖昧になり、後で「誰がそう言ったのか」を追えなくなるため。

### D5: ラフは生成後も残る。消えるのは保存時

ライフサイクルは**スライド単位のセッション状態**とする。

- 消える: Save（＝コミット）、明示削除、スライド削除
- 消えない: 生成完了、提案タブの切り替え、モードのON/OFF
- リロードで消えてよい（永続化しない）

Saveで消す理由は、保存がそのスライドを確定させる合図だから。破棄ボタンは別途設けない。

**提案タブ（複数提案／branch checkout）をまたいでも残す。** ラフは特定の案に属する落書きではなく、その場の仕様として機能する。各案をラフと照合して選びたいので、切り替えで消えると照合の軸が失われる。

### D6: ラフモード中は本体を触らせない

ラフモード中はブロック追加・インスペクタ・要素ドラッグを無効化する。オーバーレイを触っているのか本物のDOMを触っているのかが曖昧な状態を作らない。

### D7: 見え方

- ラフ矩形は**塗りなしの輪郭＋ラベル**。生成結果に重ねたときに下が読めることが条件
- 重ね表示はモードのトグルと同じキー（`R`）で切り替える

## 4. 既存実装との接続点

実装前の確認として、既存コードの制約を挙げる。

| 箇所 | 制約 |
|---|---|
| `app/page.tsx:488` | `.slide-viewport` は `host.innerHTML = …` で丸ごと書き換わる。ラフのDOMをこの中に置くと消える。**`.slide-shell` 直下の別レイヤーに置く** |
| `app/globals.css:331` | `.weave-slide` は `transform: scale(var(--slide-scale))`, `transform-origin: top left`。ラフレイヤーも同じ変換を当てれば座標系が一致する |
| `app/page.tsx:638` | ポインタ座標→スライド座標の変換は既存のドラッグ処理に前例がある（scaleで割る） |
| `app/page.tsx:338` | `contextEnvelope()` に `rough` を足せば、サーバは中身を素通しでプロンプトへ載せる（`server/local-api.mjs:98`）。ただしD3の解釈ルールは別途プロンプトに書く必要がある |
| `server/local-api.mjs:105` | `requireText` がD4の変更対象 |
| `app/page.tsx:1664` | `.canvas-toolbar` のzoom群の隣がモードトグルの置き場所 |
| `app/page.tsx:1581` | チャット入力上の `.context-chip` がラフ添付チップの置き場所 |

## 5. 未決事項

1. **既存コンテンツがあるスライドでラフを描いたときの意味** — 「作り直し（置き換え）」か「追加」か。最も単純なのは空スライドでのみラフモードに入れる案だが、作り直しの場面は実際にある
2. **同じラフでの再生成** — 結果が外れたときに同じラフで作り直すボタンが要るか、複数提案（提案軸）に寄せて済ませるか
3. **提案軸機能との実装順序** — ラフ単体で先に出すか、軸とセットで出すか
4. **ラベルなし矩形の扱い** — 「まだ何を置くか決めていない枠」として許すか、入力必須にするか

## 6. 成功条件

**空スライドから狙った構成に到達するまでの往復回数が、テキストのみの場合より減ること。**

減らないなら、人間が矩形を描く手間がそのまま純損失になる。その場合はこの機能を捨てる。
