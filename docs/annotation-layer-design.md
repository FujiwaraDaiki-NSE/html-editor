# 注釈レイヤー 設計・要件

作成日: 2026-08-09
更新日: 2026-08-10（D8・D10・D11 — ラフモードの空状態を作り直し、ラベル規則を一般化し、矢印を「関係」として予約した）
ステータス: 実装中（P0–P3 済み、P4 未着手。D8のUXパスに着手）
関連: [concept.md](../concept.md) 2.5 / 2.9 / 2.10 / 2.11

## 1. 目的

人間の頭の中にある仕様を、キャンバス上の**位置に紐づけた形**でagentに渡すためのチャネル。紙のスライドに赤ペンで囲って書き込む、あの操作にあたる。

現状、人間からagentへの入力はテキスト1本しかない。テキストは「何を言うか」は運べるが、「どこの話か」と「どれくらいの大きさか」は運べない。「もっといい感じに」が通じないのはここが原因で、逆に配置さえ渡せれば残りは今のagentで足りる。

一方で、人間がブロックを直接置いて解決することもできない。ブロックを1つ置いた瞬間に、タグ・入れ子・クラスの決定を人間が引き受けることになるからだ。まだ「左に図、右に3項目」しか決まっていない段階で、その全部に答えさせられる。

注釈レイヤーは、**位置と大きさとラベルだけを、矛盾したまま置ける場所**を作る。構造の決定はagentに残す。これは 2.11 で「flexの軸を人間に考えさせないのはツールの仕事」と決めた線を、キャンバスの外まで延ばしたものにあたる。

### 単一の枠組み

注釈は常に **対象（どこ）＋ それが何であるべきか** の組である。対象の指し方が2通りあるだけで、後段の扱いは同じになる。

| 指し方 | 入口 | 「何が」を書く場所 | 使う場面 | 例 |
|---|---|---|---|---|
| 既存要素を指す | 通常モードで `@`（D9） | 本文 | 手直し | 見出しを指して「2行に収まる長さに」 |
| 空間に矩形を描く | ラフモードでドラッグ（D10） | ラベル | 0→1、追加 | 左半分に矩形を描いて「写真」 |

**この2つを別機能として作らない。** 白紙から組む場面と手直しの場面で人間が持ち替えるものは何もなく、どちらも「ここについて、こうしてほしい」を言っているだけである。

**入口が分かれても後段は分かれない。** 配列・JSONの形・プロンプト・チップ・重ね照合・寿命はすべて共通で、違うのは対象を作るジェスチャだけ（もともと click と drag で違った）。入口を分ける理由は場面ではなく**編集を止める必要があるかどうか**で、矩形はキャンバスを描画面に変えるのでモードが要り、指差しは何も変えないので要らない（D6・D9）。

**場面はシステムの状態として持たない。** 「新規作成」「修正」のようなフローも宣言もなく、記録されるのは何を指したか（`region` か `element` か）だけで、それはどこを触ったかの結果として決まる。ラベルの書き方・JSONの形・プロンプト・重ね照合・寿命はすべて共通である（唯一分かれるのは送信の既定だが、それは場面ではなく作成コストによる区別。D7）。

場面を宣言させると、人間は描き始める前に「これは新規か修正か」を答えることになり、実質的に2機能へ戻る。既存要素の上に矩形を描いたときに置き換えなのか追加なのかも、フローではなく**ラベルが決める**（D1）。巻き込む要素は `intersects` が伝える（D4）。

## 2. スコープ

- 白紙から構成を組む（0→1）
- 既存スライドの手直し

### 非スコープ

- 描画ツールとしての作り込み（**図形の種類・線種・色・自由曲線は持たない**。D11）
- 複数スライドにまたがる注釈
- デッキの性質を常駐させる仕組み（D2）

矢印は非スコープから外れるが、**「関係」としてのみ**であって描画の道具としてではない。形と時期は D11 に置き、着手は §8 の測定より後とする。

## 3. 要件

| # | 要件 |
|---|---|
| R1 | ラフモードへ1操作で出入りできる。モード中であることが画面から明らかである（D8・D10） |
| R2 | 通常の編集モードのまま既存要素を対象にできる。入口は入力欄の `@`。何が指せるかと、今どれが取れるかが画面に出ている（D9） |
| R3 | ラフモードで空間をドラッグして矩形を描き、対象にできる |
| R4 | 矩形にラベルを書ける。描いた直後にそのまま入力できる。ラベルは任意。**要素の注釈はラベルを持たない**（D1） |
| R5 | 本文から注釈を参照できる。要素を指した参照はキャレット位置に挿入される |
| R6 | 矩形を移動・リサイズ・削除できる。要素の注釈は削除だけができる。それ以外の編集手段は持たない |
| R7 | 注釈は複数置ける。順序が人間にもagentにも分かる |
| R8 | 背景・意図を添えて送れる（チャット入力欄）。**任意**。注釈だけでも送信できる |
| R9 | 矩形の注釈を送るかどうかを送信前に選べる。状態が送信前に見えている。送るときは**全体が1つの塊**として送られる |
| R10 | 送信済みの注釈を下書きへ戻せる |
| R11 | 送信済みの注釈を呼び出し、生成結果の上に重ねて表示できる。ズレを目視でき、トグルできる |
| R12 | 注釈が消えるタイミングが1つに定まっており、明示的な後始末を要求しない |
| R13 | ラフモードに入った直後——**まだ1つも描いていない状態**——で、何をすればいいかが画面から分かる（D8） |

R11 はこの機能の中心である。注釈を置く部分だけを作って照合を作らないと、単に遠回りな指示入力になる。

R13 は R1 と別物である。R1 は「モードに入ったことに気づくか」で、R13 は「入った先で何ができるか」。**気づくことは分かることではない**ので、片方を満たしても他方は満たされない。

## 4. 設計判断

### D1: 矩形とラベルは結果を書き、指示文は理由を書く

人間が渡す情報を3つに分ける。役割が重ならないので、どこに何を書くか迷う余地がない。

| 層 | 持つもの | 例 |
|---|---|---|
| 矩形 | どこに・どれくらいの大きさで | 左半分 |
| ラベル | 何が | 写真 |
| 指示文 | なぜ・どういう資料か（背景・意図） | 経営会議向け。数字が主役。写真は現場感が出れば差し替え前提 |

**仕様（矩形＋ラベル）と意図（指示文）は、片方だけでは足りない。** ラベル「写真」だけでは大きさもトリミングもキャプションの有無も決まらないが、「現場感が出れば差し替え前提」が加わると枠だけ置くという判断ができる。逆に意図だけでは配置が決まらない。agentは**仕様の隙間を意図で埋める**。この関係が成り立つのは両者の役割が重なっていないからで、1つのフィールドに混ぜると失われる。

**ラベルは、対象が自分で語れないときに出る。** これが規則の一般形で、対象の種別ごとの例外ではない。

| 対象 | 自分で語れるか | ラベル |
|---|---|---|
| 要素 | 語れる（種別と本文の抜粋が送信時点の中身を運ぶ。D4） | 持たない |
| 矩形 | 語れない（中身がまだ存在しない） | 「何が入るか」を書く。任意 |
| 関係（D11） | 語れない（関係の種類は端点から導けない） | 「どういう関係か」を書く。任意 |

要素にもラベル欄を出すと、同じ対象について語る場所が**ラベルと本文の2つ**になり、どちらに書くか決まらないうえ、目の前の空欄が「もっと詰めて」という手順の記述を誘う（上の規則が禁じている書き方）。したがって要素の注釈は**指すだけ**で、言いたいことは本文が引き受ける。三者は同じ配列に同じ形で入り、要素では `label` が空のまま送られる。これは規約ではなく構造で、要素にはラベルのUIを出さない。

この非対称は D7-a の「参照の挿入は要素のときだけ」と同じ根拠に立つ。要素は文の主語になるから本文で語られ、矩形は埋める枠だからラベルで足りる。書く場所が対象の種別から一意に決まる。

**空のラベルの意味は種別で違う。** ラベルのない矩形は座標しか残らないが、ラベルのない関係は「関係がある」という事実を運ぶ。だから矢印のラベルも任意でよく、既定は空でよい（D11）。

**ラベルは例文で教える。** 「結果を書き、手順を書かない」は設計書の中の規則であって画面には出ていない。プレースホルダに例を2つ置くだけで、規則を読ませずに同じことが起きる（D8）。

**ラベルは結果を書き、手順を書かない。** 手直しで「もっと詰めて」と書きたくなる場面では「1行に収まった数字帯」と書く。これは 2.10 で記述的（絶対配置）でなく宣言的を選んだのと同じ骨格であり、理由も同じ——結果だけ与えられた方がagentは寛容に振る舞える。

この規則により、**枠組みが場面によって意味を変えない**。0→1ではまだ存在しないものの結果を書き、手直しでは今と違う結果を書く。どちらもラベルは「そこがどうあるべきか」であって、2つの場面を1機能で扱える根拠はここにある。

ラベルの粒度＝確定度の素直な対応にする。「Q3の要点 3つ」なら3項目のプレースホルダ、「前年比 118%」ならその数字が入る。

### D2: 指示文は注釈ごとに持たない。置き場所はチャット入力欄

背景・意図は局所化しない。「経営会議向け」は特定の矩形の性質ではなくスライドやデッキの性質なので、注釈ごとの指示文フィールドは作らない。データはフラットな配列＋ターンの属性1つで足りる。

置き場所は**チャット入力欄のまま**とし、専用のUIも保存先も作らない。同一Threadなら一度言えば会話履歴として以降のターンでも見えているため、この機能の範囲では追加の仕組みを必要としない。

（この機能に要らないというだけで、デッキの性質を常駐させる仕組み自体は別途あり得る。concept.md 3節「Skillsの共有の仕組み」に属する話で、ここでは扱わない）

### D3: 注釈は真実に混ぜない

`slides/*.html` にも `.weave/deck.json` にも書かない。保存対象外、git対象外、**undo対象外**。

undoから外す理由は、undoの実体がHTMLスナップショットだから（2.10）。注釈はHTMLではないので、混ぜるとundo1回の意味が二重になる。描き間違いは Delete で消す。

### D4: 表現は1280×720座標＋交差要素

```
{
  id: string,
  order: number,              // 人間に見える通し番号と一致
  target: { kind: "element", weaveId: string, elementKind: string, textExcerpt: string }
        | { kind: "region" }
        | { kind: "link", from: string, to: string },   // 注釈idの組（D11・未実装）
  rect: { x: number, y: number, w: number, h: number },   // 送信時点の外形
  label: string,              // 結果の記述（D1）
  intersects: string[]        // rect が重なる既存要素の weave-id
}[]
```

指示文はこの配列の外に置く。注釈の属性ではなくターンの属性だからである（D2）。

**`rect` は両方の対象種別が持つ。** 要素を指した注釈でも外形は送信時に記録している（D8、重ね表示のフォールバックに要る）ので追加コストはなく、agentは `data-weave-id` を引き当てるまでもなく「左側の幅広の箱の話だ」と位置関係で読める。座標の有無で2種類の扱いが分岐しないことにもなる。

ただし**役割は同じではない**。`element` では参照の本体は `weaveId` である。種別と本文の抜粋がidをスライドHTMLへ引き当てなくても「何を指したか」をその場で読めるようにし、`rect` は位置関係を伝える。スライドHTMLはファイルにあるため、envelopeで二重に運ばない。どちらも送信時点のスナップショットであり、agentが要素を動かせば古くなるので、idと食い違ったら**idを優先**する。`region` では `rect` が参照そのもので、他に指す手段がないため要素情報を持たない。

この2つは排他ではなく、**指した先にどれだけ既存の同一性があるか**の連続として並ぶ。`intersects` がその橋渡しで、座標からidを導出する。

| 指した先 | agentに渡るもの |
|---|---|
| 既存要素 | id（確実）＋ 種別＋本文の抜粋 ＋ rect |
| 既存要素に重なる矩形 | rect ＋ 導出したid |
| 白紙に描いた矩形 | rect のみ |
| 関係（D11） | 端点の注釈id2つ ＋ ラベル |

分岐しているのは何が手に入るかだけで、人間の操作もデータの形も同じである（§1）。

`link` の `rect` は端点の外接矩形とし、**導出値**として持つ（重ね表示のフォールバックに要るだけで、参照の本体ではない）。`intersects` は空。座標は関係の表現に一切使わない（D11）。

agentには画像を送らず、このJSONを送る。2.9で設計サイズを1280×720に固定し絶対pxで書くと決めているため、**注釈の座標系はagentがCSSを書く座標系とそのまま同一**になる。ビジョンモデルへの依存が要らないのはこの決定の副産物であり、可変ビューポート前提のツールでは同じ形が取れない。

`intersects` は手直しで効く。「この範囲」が既存のどの要素にかかっているかをクライアント側で解決して渡すことで、agentが対象を取り違えにくくなる。範囲と要素は排他ではなく、**範囲は要素を巻き込む**という関係で扱う。

### D5: 座標を絶対配置で再現させない

**最大の落とし穴。** 座標を渡すと、agentは座標を忠実に再現しようとして絶対配置CSSを書きうる。これは 2.10 で「宣言的フローを選ぶ核心理由はagentにとって寛容だから」と決めた方針と正面衝突する。

したがってプロンプトで明示する:

- 矩形は**比率と順序の近似**であって、座標の指定ではない
- 出力は Row / Column / Grid のフロー構造であること
- 揃っていない・重なっている矩形を整えるのはagentの仕事であること

### D6: ラフモードは矩形専用。指差しはモードを必要としない

**選択は指す行為であって変更ではない。** ならば指すためにモードへ入る理由がない。要素の指差しは通常の編集モードに置き、ラフモードは矩形を描くためだけのものとする（D9）。

そう分ける根拠は**キャンバスに何をさせるか**である。矩形はキャンバスを描画面に変えるので、ドラッグ並べ替えや contenteditable と同じジェスチャを奪い合う。モードはその衝突を解く手段であって、指差しには最初から衝突がない。

その結果、ラフモード中のキャンバスは**完全に不活性**になる。インスペクタ・ドラッグ並べ替え・contenteditable に加えて要素の選択も要らず、「オーバーレイを触っているのか本物のDOMを触っているのか」という曖昧さが状態としてなくなる。

不活性であること自体は画面から見えないので、**押しても何も起きないという無反応は、説明がないと故障に見える**。その説明を D8 の紙が引き受ける。

（旧版ではモード中も選択を生かしていた。指差しがモードの外に出た時点で、その例外は不要になった）

### D7: 注釈はチャットの下書きの一部。送信で消費と表示が同時に終わる

注釈をキャンバスの持ち物として扱うと、コンテキストに載る寿命と画面に見えている寿命がずれ、いつ消えるのかを説明できなくなる。**注釈はテキスト入力欄と並ぶ下書きである**と捉える。

- テキストは入力欄に書く／注釈はキャンバスに書く。どちらも未送信の下書き
- 送信で両方が送られ、両方がクリアされる

不変条件は1つだけになる。**キャンバスに見えている注釈＝未送信の下書き。** 文字を打って送れば入力欄が空になるのと同じ挙動なので、追加の説明を要しない。

**送信の既定は指し方で分かれる（R9）。**

| 指し方 | 既定 | 制御 |
|---|---|---|
| 要素の選択 | 常に送る | 無し |
| 矩形 | 送る（ON） | 入力欄上のチップでOFFにできる |

分ける基準は**失われたときの作り直しコスト**である。選択はクリック1回で作り直せるので制御する価値がなく、既存の `contextEnvelope.selected` がすでにそう振る舞っている。矩形は描いてラベルを打った手作業なので、消費させない選択肢を残す。

これは§1の「場面をシステムの状態として持たない」への例外ではない。0→1と手直しという**場面**の区別ではなく**作成コスト**の区別であり、データの形・ラベルの書き方・重ね照合はすべて共通のままである。分岐はこの1箇所に限る。

**送るときは注釈全体が1つの塊になる。** 要素を指した注釈も矩形と同じ塊に入る（§1）。

配送を塊に固定するのは、**トークンを配送手段にしないため**である。個々の注釈を `@①` として本文に埋め込み、埋め込まれたものだけを送る形は採らない。

- 「描いたがトークンが無い注釈」という第3の状態が生まれ、矩形とトークンを1対1で連動させる規則が要る
- 入力欄を `<textarea>` から contenteditable のコンポーザへ作り替えることになる（IME合成の扱いを含む。`app/page.tsx:1596`）

### D7-a: 配送と言及を分ける

配送が塊に固定されている前提でなら、本文から個々の注釈を参照してよい。**参照は「送るかどうか」ではなく「本文の主語にするかどうか」を決めるだけ**であり、参照されなかった注釈も塊に入って送られる。上の2つの代償はどちらも発生しない。プレーンテキストの `@見出し` を挿入すれば足りるので、コンポーザも現状のままでよい。

**参照の挿入は要素を指したときだけ行う。** 既存要素は語る対象として指されるので文の主語になる（「`@2` を2行に収まる長さに」）。矩形は埋める枠として置かれるのでラベルで足り、描いても挿さない（番号での参照は可能）。

要素では**指す操作そのものが参照の挿入**である。入口が入力欄の `@` なので（D9）、書きかけの文にキャレット位置から続く。「指してから、それについて書く」が1つの動作になる。

本文から `@2` を消しても注釈は下書きに残る。D7-a の原則どおり参照は言及であって配送ではなく、文字の削除と注釈の削除を連動させると、D7 が退けた「トークンと注釈の1対1連動」に戻ってしまう。要素の注釈を取り消す場所はキャンバスの枠とチップのレジェンドである。

**矩形を参照した時点でチップをONに戻す。** チップをOFFにしたまま本文が `@1` を参照すると、参照だけが入って矩形が送られず、本文が宙に浮く。言及すること自体が「含める」という明示にあたる。

### D7-b: 送信済みの注釈は下書きへ戻せる（R10）

矩形の既定をONにする以上、誤送信からの回復手段が要る。送信済み注釈はメッセージの添付として手元のメモリにあるので、下書きへコピーし直すだけでよく、新しい保存先も履歴も要らない。**この安全網があって初めて既定ONを選べる**という依存関係にある。

消えるのは以下。

- **送信**（主たる経路。矩形はチップONのとき）
- 個別のDelete、スライド削除、リロード

チップOFFで送ったメッセージは矩形に触れない。無関係な質問を挟んでも下書きは残る。

Save・生成完了・提案タブの切り替え・モードのON/OFFは注釈に触れない。Undo/Redoも何もしない（D3）。

**送信済みの注釈は、メッセージに添付1つとして残る。** R11の重ね照合は、キャンバスの常設状態ではなくそのメッセージから呼び出す。何ターンも後に「あのとき何を指したか」を見返せるので、記録としてはむしろ強くなる。添付はクライアントのメモリにのみ持ち、リロードで失われてよい（D3と揃う）。

この形により、次の3つが設計から消える。

1. Saveと注釈の関係（Saveは注釈に一切関与しない）
2. 提案タブ切り替え時の扱い（キャンバスに常設のものが無い）
3. 対象要素がagentに消されたときの追従（送信時点のジオメトリをスナップショットすれば足りる）

### D8: 見え方

#### 注釈そのもの

- 矩形は**塗りなしの輪郭＋通し番号＋ラベル**。生成結果に重ねたときに下が読めることが条件
- 要素を対象にした注釈は、その要素の外形をなぞる形で表示する（矩形と同じ見た目に揃える）。**通し番号だけを付け、ラベルは出さない**（D1）。通常モードでも下書きにある限り見えている
- 送信時にその外形を1280×720座標で記録し、以後の重ね表示はその記録を使う
- 送信済み注釈の重ね表示は、チャットの該当メッセージから呼び出してトグルする

#### ラフモードの面（R1）

**モードの表示は、面が変わることでしか伝わらない。** 現状の合図はステータス行・ツールバー・インスペクタの注意書きの3つで、いずれもキャンバスの外にある。視線はスライドの中央にあるので、周辺の変化は気づかれない。

面は**注釈レイヤーが持つ**。`.annotation-overlay-layer` はもともとスライドの兄弟にある別レイヤーで（§5・D9）、空のあいだ透明なので**紙がそこにあること自体が見えていない**だけである。ここに実体を与える。

- 下のスライドから**彩度を抜く**（`backdrop-filter`）。塗るのではない
- インクはこのレイヤーの子なので影響を受けず、**彩度を持つのは注釈だけ**になる
- ビューポートに内側のリングを1本足す（視線が中央にあるときの保険）
- 面は 160ms で入る。**「今、切り替わった」を伝える本体は動きである**

**一色のベタ塗りにはしない。** デッキの地色は固定できず（同一デッキに `#020617` と `#fff` のスライドが同居する）、白い膜も黒い膜も半分のスライドで効かない。彩度を抜く方式は地色に依存せず、明暗が保たれるので**既存要素の上に矩形を描く手直しでも下が読める**。読めることは D5 の前提でもある。

効果をスライドではなくレイヤーに置くことで、スライドのDOMにもキャンバスの処理にも触らずに済む（D6 の線が保たれる）。

#### 空状態のゴースト（R13）

面が変わっても「ここは描ける場所だ」までしか言えない。残りは紙の上に書く。

**注釈が0件のときだけ**、紙の中央に手順を出し、1つ目を描いた瞬間に消す。

- 「ドラッグで枠を描く → そこに何が入るかを書く」——2段階（D1）はこの機能の骨格なので、ここで教える
- 「描いた枠はまとめて Agent へ渡ります」——これが指示だと分かる場所が他にない。チップの `N regions · Send` は描いたあとにしか出ない

空状態にしか出ないので、慣れた人の邪魔を一度もしない。

#### ラベルのプレースホルダ

`Label` の一語をやめ、例を2つ入れる（`何が入る？（例：写真、1行に収まった数字帯）`）。**何を書けばいいか分からない空欄は、「もっと詰めて」のような手順の記述を誘う**——D1 が禁じている書き方である。粒度＝確定度の対応（D1）も例文がそのまま見せる。

#### 語彙：モードは面、モードでないものは部品

| 状態 | 合図 | 意味 |
|---|---|---|
| ラフモード | 面が変わる（紙） | 編集面が引っ込んでいる。触っても何も起きない（D6） |
| 指し待ち | 部品が出る（候補の枠） | 編集面は生きている。選べるものが増えただけ（D9） |

D9 が「指し待ちで中身を暗くしない」と決めているのと衝突しない。**面が変わったらキャンバスは不活性**という対応が一貫するので、後から指示面に何かを足すときも、どちらの見せ方かが自動的に決まる。

### D9: 指差しの入口と可視化

`@` を入口にする。入力欄で `@` を打つとキャンバスが**指し待ち**になり、要素を1つ押すと参照がキャレット位置に入る。プレーンテキストの挿入で足りるので、D7 が避けたコンポーザの contenteditable 化は要らない。

**発見は選択から教える。** 機能を知らない人でも要素はクリックする。選択中のステータス行に押せる `@` を出し、押せば参照が入り、ラベルに書かれた `@` が次からのキーを教える。知らない人の経路と知っている人の経路が同じ結果に着く。

**指し待ちの間は、指せるものを全部見せる。** 対象の候補（`data-weave-id` を持つ要素）すべてに枠を描く。1280×720のスライドは1枚あたり数個〜十数個なので、全部出しても読めるし、**このスライドが何個の部品でできているか**が一目で分かる。枠が一斉に出ること自体が状態変化の合図にもなる。

- **中身は暗くしない。** 何を指すかはスライドを読んで決めるので、スクリムで覆うと選べない。状態はビューポートの枠・カーソル・ステータス行が伝える
- **枠の内側を押すと最も内側の要素**が取れる。枠はDOM順（親→子）で描くので、子が親の上に重なり、当たり判定が自然に内側優先になる
- **枠のタブ（左上の名札）を押すとその枠自身**が取れる。入れ子で重なった親を取る手段がこれにあたる。タブには種別と本文の抜粋を出す（`h2 · 四半期の要点`）
- ホバー中の枠だけを実線にする。常設の枠はヘアラインに留め、「今押したらどれ」の確定はホバーが担う
- すでに指した要素のタブには `@2` を出す。同じ要素を再び押しても増えず、既存の注釈が選ばれる
- Esc、または枠のない場所を押すと指し待ちを抜ける
- `@` の検出は**IME合成中に発火させない**。既存の `compositionRef` と同じガードを通す

枠は注釈オーバーレイ層に描き、**本物のDOMには一切触らない**。座標系は `--slide-scale` で一致しており（§5）、要素の矩形は `intersects` 算出で使う `liveAnnotationBoxes()` がすでに集めている。D6 の線がそのまま保たれる。

### D10: 「注釈」は傘、「ラフモード」は行為

UIのラベルは**カテゴリではなく行為**を名乗る。

§1のとおり「注釈」は傘の名前で、`@`（既存要素を指す）と矩形（空間を指す）の両方を含む。一方で「注釈モード」はそのうち矩形だけを指していた。**傘と、傘の下の片方が、同じ語を使っていた**ことになる。モードが要るのは矩形だけという実装の都合が語彙に漏れた形で、画面を見る側には知りようがない。

- **UI**（ツールバー・ステータス行・インスペクタの注意書き・ショートカット一覧・README）は「ラフ」
- **データとコード**（`annotations[]`・`annotationEnvelope`・`data-annotation-mode`・`.annotation-*`）は「注釈」のまま。両方を1つの配列に入れるという設計そのものなので変えない

`@` 側には名前を与えない。名前を付けた瞬間に「2つの機能」に見え始め、§1で避けたところへ戻る。ステータス行の状態表示（`参照する要素をクリック`）で足りる。

副産物として、「モード」という語が指すものが1つだけになる（`@` はモードではない。D6）。

### D11: 関係は辺であって、線ではない

矩形をいくつ並べても言えないことが1つある。**要素どうしの関係**である。「この3つはこの順に流れる」「ここをあそこへ動かす」「この枠はこの見出しの補足」は、`rect` と `label` の組では表現できない。プロセス図・フロー・引き出し線はスライドの主要な語彙なので、これは実際の穴にあたる。

したがって矢印を1種類だけ持つ。ただし**作り方を間違えると、ここが描画ツールへの入口になる**。

| | 形 | agentに渡るもの |
|---|---|---|
| 採る | 2つの注釈を結ぶ辺。`{ kind: "link", from, to }` | グラフ。「①から②へ」と読める |
| 採らない | `x1,y1,x2,y2` の自由な線 | 座標。何と何を結ぶかを推測させる |

後者は D5 が防いでいる「座標の忠実な再現」に最も近い形である。`intersects` が座標からidを導出しているのと同じ発想で、**関係もidの組で持つ**。

- **端点は必ず注釈**。空間には向けられない。空いた場所を指したいなら先に矩形を描く。これで注釈の集合が閉じたグラフになり、座標から関係を推測する経路が最初から存在しない
- **要素・矩形のどちらも端点になれる。** むしろ**要素→矩形**（「この見出しを、右のこの枠へ」）が一番効く。手直しと0→1が1本で繋がる
- **ツールパレットは作らない。** 「矩形ツール／矢印ツール」を並べた瞬間、§1の「描き始める前に選ばせる」が戻る。枠にホバーすると出るコネクタを別の枠までドラッグする——矢印は「描く」のではなく「つなぐ」ものなので、ジェスチャと意味が一致する
- **通し番号は共用。** 同じ配列に入るので `@3` で本文から参照できる（D7-a のまま）
- ラベルは任意で既定は空（D1）

**プロンプトに1行足す必要がある。矢印は「矢印を描け」という意味ではない。** 「①→②」は多くの場合「この順に読ませろ」であって、スライドに矢印グラフィックを置けという指示ではない。表現の選択はagentに残す——順序・隣接・グルーピングで表してもよい。literalな矢印が欲しいときは人間がラベルにそう書く。D5と同じ調子で `annotationPromptRules` に置く。

**図形の種類と線種は持たない（§2）。** PowerPointで図形が要るのは描いた図形がそのまま出力だからで、ここでは描いたものは指示にすぎない。楕円に「写真」と書いても矩形に「写真」と書いてもagentの出力は同じなので、形は情報として空である。空なだけでなく、描く前に「四角か丸か」を選ばせるコストが乗り、PPTに似るほどliteralな再現を期待させて D5 を打ち消す。**素っ気ない矩形は、ラフさ自体が「これは近似だ」を伝えている。** 線種も同様で、意味はラベルの方が正確に運べるうえ、線種はすでに対象の種別を表す軸として使用中である（実線＝矩形／破線＝要素／二重線・点線＝送信済みの重ね表示）。

**着手は §8 の測定より後とする。** 矩形＋ラベルだけで往復回数が減らないなら矢印を足しても減らない。減るなら「何が足りなかったか」が実測で出るので、次に足すものもデータで決まる。ここに書いてあるのは**形の予約**であり、いま実装するものではない。D3で永続化しないと決めてあるためスキーマ追加のコストはゼロで、先に一般化しておく必要もない。

## 7. 位置づけ：キャンバスの二面性

この機能が導入しているのは「ラフを描く機能」ではなく、キャンバスの**二面性**である。

- **編集面** — 人間が直接DOMを変える（選択・ドラッグ・contenteditable・インスペクタ）
- **指示面** — 人間がagentに向けて指す・書く

D6は、この二面を分ける線を引いたものにあたる。**指示面はモードと同義ではない。** 矩形は編集面のジェスチャを奪うのでモードで隔てるが、指差しは奪わないので編集面と同居する（D9）。分ける基準はキャンバスに何をさせるかであって、指示か編集かではない。

矩形＋ラベルは指示面に置ける最初の1種類にすぎず、後から次のようなものが同じ面に載りうる。

- **要素間の関係（矢印）** — 形は D11 で予約済み。辺として持ち、線としては持たない
- 参照画像の貼り付け
- **agentからの書き込み** — 「ここは指示が曖昧だった」「この2案で迷った」が位置に紐づいて返る。指示面が共有されると、人間→agentの一方通行が双方向になる

なお、指差しの最も細い形は既に動いている。`contextEnvelope.selected` が選択中の要素の `data-weave-id` を毎ターン渡しており（`app/page.tsx:341`）、その属性は保存後の `slides/*.html` にも残る（`app/page.tsx:292`／agentへの指示は `server/project.mjs:64`）ため、agentは実ファイル上で対象を引き当てられる。**解決の経路は既にあり、R2が足すのは数と明示性と意図である。**

| | 現状 | 注釈レイヤー |
|---|---|---|
| 数 | 1つだけ（`selectedId` は単数） | 複数 |
| 明示性 | 暗黙。何が送られたか画面に出ない | 下書きに列挙され、本文から参照される（R5） |
| 意図 | 無い。本文と対象が1対1でしか対応しない | 対象ごとに結び付く（要素は本文の参照、矩形はラベル） |

**拡張に備えてスキーマを一般化する必要はない。** D3で永続化しないと決めたため、後から `target.kind` や発信者の区別を足すコストはゼロで、移行も互換も発生しない。概念として認識しておけば足り、今作るのは矩形とラベルだけでよい。

## 8. 成功条件

**狙った状態に到達するまでの往復回数が、テキストのみの場合より減ること。**

0→1と手直しの両方で測る。減らないなら、人間が注釈を置く手間がそのまま純損失になる。その場合はこの機能を捨てる。
