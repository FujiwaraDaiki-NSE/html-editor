# 注釈レイヤー 設計・要件

作成日: 2026-08-09
ステータス: 要件定義／基本設計（未実装）
関連: [concept.md](../concept.md) 2.5 / 2.9 / 2.10 / 2.11

## 1. 目的

人間の頭の中にある仕様を、キャンバス上の**位置に紐づけた形**でagentに渡すためのチャネル。紙のスライドに赤ペンで囲って書き込む、あの操作にあたる。

現状、人間からagentへの入力はテキスト1本しかない。テキストは「何を言うか」は運べるが、「どこの話か」と「どれくらいの大きさか」は運べない。「もっといい感じに」が通じないのはここが原因で、逆に配置さえ渡せれば残りは今のagentで足りる。

一方で、人間がブロックを直接置いて解決することもできない。ブロックを1つ置いた瞬間に、タグ・入れ子・クラスの決定を人間が引き受けることになるからだ。まだ「左に図、右に3項目」しか決まっていない段階で、その全部に答えさせられる。

注釈レイヤーは、**位置と大きさとラベルだけを、矛盾したまま置ける場所**を作る。構造の決定はagentに残す。これは 2.11 で「flexの軸を人間に考えさせないのはツールの仕事」と決めた線を、キャンバスの外まで延ばしたものにあたる。

### 単一の枠組み

注釈は常に **対象（どこ）＋ ラベル（何が）** の組である。対象の指し方が2通りあるだけで、後段の扱いは同じになる。

| 指し方 | 使う場面 | 例 |
|---|---|---|
| 既存要素を選ぶ | 手直し | 見出しを選んで「2行に収まる長さ」 |
| 空間に矩形を描く | 0→1、追加 | 左半分に矩形を描いて「写真」 |

**この2つを別機能として作らない。** 白紙から組む場面と手直しの場面で人間が持ち替えるものは何もなく、どちらも「ここについて、こうしてほしい」を言っているだけである。

**場面はシステムの状態として持たない。** 「新規作成」「修正」のようなフローも宣言もなく、記録されるのは何を指したか（`region` か `element` か）だけで、それはどこを触ったかの結果として決まる。ラベルの書き方・JSONの形・プロンプト・重ね照合・寿命はすべて共通で、分岐は存在しない。

場面を宣言させると、人間は描き始める前に「これは新規か修正か」を答えることになり、実質的に2機能へ戻る。既存要素の上に矩形を描いたときに置き換えなのか追加なのかも、フローではなく**ラベルが決める**（D1）。巻き込む要素は `intersects` が伝える（D4）。

## 2. スコープ

- 白紙から構成を組む（0→1）
- 既存スライドの手直し

### 非スコープ

- 描画ツールとしての作り込み（色・線種・自由曲線・矢印は持たない）
- 複数スライドにまたがる注釈
- デッキの性質を常駐させる仕組み（D2）

## 3. 要件

| # | 要件 |
|---|---|
| R1 | 注釈モードへ1操作で出入りできる。モード中であることが画面から明らかである |
| R2 | 既存要素をクリックして対象にできる |
| R3 | 空間をドラッグして矩形を描き、対象にできる |
| R4 | 各注釈にラベルを書ける。対象を確定した直後にそのまま入力できる。ラベルは必須 |
| R5 | 注釈を移動・リサイズ・削除できる。それ以外の編集手段は持たない |
| R6 | 注釈は複数置ける。順序が人間にもagentにも分かる |
| R7 | 背景・意図を添えて送れる（チャット入力欄）。**任意**。注釈だけでも送信できる |
| R8 | 注釈を送るかどうかを送信前に選べる。選択の状態が送信前に見えている |
| R9 | 送信済みの注釈を呼び出し、生成結果の上に重ねて表示できる。ズレを目視でき、トグルできる |
| R10 | 注釈が消えるタイミングが1つに定まっており、明示的な後始末を要求しない |

R9 はこの機能の中心である。注釈を置く部分だけを作って照合を作らないと、単に遠回りな指示入力になる。

## 4. 設計判断

### D1: 矩形とラベルは結果を書き、指示文は理由を書く

人間が渡す情報を3つに分ける。役割が重ならないので、どこに何を書くか迷う余地がない。

| 層 | 持つもの | 例 |
|---|---|---|
| 矩形 | どこに・どれくらいの大きさで | 左半分 |
| ラベル | 何が | 写真 |
| 指示文 | なぜ・どういう資料か（背景・意図） | 経営会議向け。数字が主役。写真は現場感が出れば差し替え前提 |

**仕様（矩形＋ラベル）と意図（指示文）は、片方だけでは足りない。** ラベル「写真」だけでは大きさもトリミングもキャプションの有無も決まらないが、「現場感が出れば差し替え前提」が加わると枠だけ置くという判断ができる。逆に意図だけでは配置が決まらない。agentは**仕様の隙間を意図で埋める**。この関係が成り立つのは両者の役割が重なっていないからで、1つのフィールドに混ぜると失われる。

ラベルは必須とする。対象だけの注釈は何も言っていない。

**ラベルは結果を書き、手順を書かない。** 手直しで「もっと詰めて」と書きたくなる場面では「1行に収まった数字帯」と書く。これは 2.10 で記述的（絶対配置）でなく宣言的を選んだのと同じ骨格であり、理由も同じ——結果だけ与えられた方がagentは寛容に振る舞える。

この規則により、**枠組みが場面によって意味を変えない**。0→1ではまだ存在しないものの結果を書き、手直しでは今と違う結果を書く。どちらもラベルは「そこがどうあるべきか」であって、2つの場面を1機能で扱える根拠はここにある。

ラベルの粒度＝確定度の素直な対応にする。「Q3の要点 3つ」なら3項目のプレースホルダ、「前年比 118%」ならその数字が入る。

### D2: 指示文は注釈ごとに持たない。置き場所はチャット入力欄

背景・意図は局所化しない。「経営会議向け」は特定の矩形の性質ではなくスライドやデッキの性質なので、注釈ごとの指示文フィールドは作らない。データはフラットな配列＋ターンの属性1つで足りる。

置き場所は**チャット入力欄のまま**とし、専用のUIも保存先も作らない。同一Threadなら一度言えば会話履歴として以降のターンでも見えているため、この機能の範囲では追加の仕組みを必要としない。

（この機能に要らないというだけで、デッキの性質を常駐させる仕組み自体は別途あり得る。concept.md 3節「Skillsの共有の仕組み」に属する話で、ここでは扱わない）

### D3: 注釈は真実に混ぜない

`slides/*.html` にも `.weave/deck.json` にも書かない。保存対象外、git対象外、**undo対象外**。

undoから外す理由は、undoの実体がHTMLスナップショットだから（2.10）。注釈はHTMLではないので、混ぜるとundo1回の意味が二重になる。描き間違いは Delete で消す。

### D4: 表現は1280×720座標＋交差要素

```
{
  id: string,
  order: number,              // 人間に見える通し番号と一致
  target: { kind: "element", weaveId: string }
        | { kind: "region" },
  rect: { x: number, y: number, w: number, h: number },   // 送信時点の外形
  label: string,              // 結果の記述（D1）
  intersects: string[]        // rect が重なる既存要素の weave-id
}[]
```

指示文はこの配列の外に置く。注釈の属性ではなくターンの属性だからである（D2）。

**`rect` は両方の対象種別が持つ。** 要素を指した注釈でも外形は送信時に記録している（D8、重ね表示のフォールバックに要る）ので追加コストはなく、agentは `data-weave-id` を引き当てるまでもなく「左側の幅広の箱の話だ」と位置関係で読める。座標の有無で2種類の扱いが分岐しないことにもなる。

agentには画像を送らず、このJSONを送る。2.9で設計サイズを1280×720に固定し絶対pxで書くと決めているため、**注釈の座標系はagentがCSSを書く座標系とそのまま同一**になる。ビジョンモデルへの依存が要らないのはこの決定の副産物であり、可変ビューポート前提のツールでは同じ形が取れない。

`intersects` は手直しで効く。「この範囲」が既存のどの要素にかかっているかをクライアント側で解決して渡すことで、agentが対象を取り違えにくくなる。範囲と要素は排他ではなく、**範囲は要素を巻き込む**という関係で扱う。

### D5: 座標を絶対配置で再現させない

**最大の落とし穴。** 座標を渡すと、agentは座標を忠実に再現しようとして絶対配置CSSを書きうる。これは 2.10 で「宣言的フローを選ぶ核心理由はagentにとって寛容だから」と決めた方針と正面衝突する。

したがってプロンプトで明示する:

- 矩形は**比率と順序の近似**であって、座標の指定ではない
- 出力は Row / Column / Grid のフロー構造であること
- 揃っていない・重なっている矩形を整えるのはagentの仕事であること

### D6: 注釈モードでは選択はできるが編集はできない

R2 のため、モード中も要素の選択は生きている必要がある。一方でインスペクタ・ドラッグ並べ替え・contenteditable は無効化する。

**選択は指す行為であって変更ではない**、という線で切る。オーバーレイを触っているのか本物のDOMを触っているのかが曖昧な状態は作らない。

### D7: 注釈はチャットの下書きの一部。送信で消費と表示が同時に終わる

注釈をキャンバスの持ち物として扱うと、コンテキストに載る寿命と画面に見えている寿命がずれ、いつ消えるのかを説明できなくなる。**注釈はテキスト入力欄と並ぶ下書きである**と捉える。

- テキストは入力欄に書く／注釈はキャンバスに書く。どちらも未送信の下書き
- 送信で両方が送られ、両方がクリアされる

不変条件は1つだけになる。**キャンバスに見えている注釈＝未送信の下書き。** 文字を打って送れば入力欄が空になるのと同じ挙動なので、追加の説明を要しない。

**ただし添付は自動では起きない（R8）。** 注釈が1件以上あるとチャット入力欄の上に添付チップが出て、それをONにした送信でだけ注釈が送られ、クリアされる。既定はOFF。

既定をOFFにするのは、2方向の事故のコストが非対称だから。誤って送ってしまえば描きかけの下書きが消費されて失われるが、付け忘れは位置の伝わらない結果を見れば気づけ、添付して送り直せば済む。**失うものがあるのは前者だけ**なので、1クリックの手間はそちらを防ぐ側に払う。

消えるのは以下。

- **注釈を添付した送信**（主たる経路）
- 個別のDelete、スライド削除、リロード

添付OFFで送ったメッセージは注釈に触れない。無関係な質問を挟んでも下書きは残る。

Save・生成完了・提案タブの切り替え・モードのON/OFFは注釈に触れない。Undo/Redoも何もしない（D3）。

**送信済みの注釈はメッセージに添付として残る。** R9の重ね照合は、キャンバスの常設状態ではなくそのメッセージから呼び出す。何ターンも後に「あのとき何を指したか」を見返せるので、記録としてはむしろ強くなる。添付はクライアントのメモリにのみ持ち、リロードで失われてよい（D3と揃う）。

この形により、次の3つが設計から消える。

1. Saveと注釈の関係（Saveは注釈に一切関与しない）
2. 提案タブ切り替え時の扱い（キャンバスに常設のものが無い）
3. 対象要素がagentに消されたときの追従（送信時点のジオメトリをスナップショットすれば足りる）

### D8: 見え方

- 矩形は**塗りなしの輪郭＋通し番号＋ラベル**。生成結果に重ねたときに下が読めることが条件
- 要素を対象にした注釈は、その要素の外形をなぞる形で表示する（矩形と同じ見た目に揃える）。送信時にその外形を1280×720座標で記録し、以後の重ね表示はその記録を使う
- 送信済み注釈の重ね表示は、チャットの該当メッセージから呼び出してトグルする

## 6. 未決事項

1. **同じ注釈での再生成** — 結果が外れたときに同じ注釈で作り直すボタンが要るか、複数提案（提案軸）に寄せて済ませるか
2. **提案軸機能との実装順序** — 注釈レイヤー単体で先に出すか、軸とセットで出すか
3. **送信済み注釈をキャンバスに戻せるようにするか** — 既定OFF（D7）で誤送信は起きにくくなったが、起きたときの回復手段が無い。メッセージから下書きへ戻す操作を持たせるか
4. **手直しでの `intersects` の粒度** — 範囲が入れ子の親子両方にかかったとき、どこまで渡すか（最も内側だけか、階層ごとか）

### 既知の制約（この機能の外）

`variations/generate` は毎回 `codex.startThread` で新しいThreadを立てる（`server/local-api.mjs:109`）。チャット入力欄で述べた背景は会話履歴なので、複数提案の生成には引き継がれない。`contextEnvelope` は variation にも付いているため、必要になったら envelope 側で解決できる。**提案軸機能を作るときに再検討する。**

## 7. 位置づけ：キャンバスの二面性

この機能が導入しているのは「ラフを描く機能」ではなく、キャンバスの**二面性**である。

- **編集面** — 人間が直接DOMを変える（選択・ドラッグ・contenteditable・インスペクタ）
- **指示面** — 人間がagentに向けて指す・書く

D6の「選択はできるが編集はできない」は、この二面を分ける線を引いたものにあたる。矩形＋ラベルは指示面に置ける最初の1種類にすぎず、後から次のようなものが同じ面に載りうる。

- 要素間の関係（矢印）
- 参照画像の貼り付け
- **agentからの書き込み** — 「ここは指示が曖昧だった」「この2案で迷った」が位置に紐づいて返る。指示面が共有されると、人間→agentの一方通行が双方向になる

なお、指差しの最も細い形は既に動いている。`contextEnvelope.selected` が選択中の要素の `data-weave-id` を毎ターン渡しており（`app/page.tsx:341`）、その属性は保存後の `slides/*.html` にも残る（`app/page.tsx:292`／agentへの指示は `server/project.mjs:64`）ため、agentは実ファイル上で対象を引き当てられる。**解決の経路は既にあり、R2が足すのは数と明示性と意図である。**

| | 現状 | 注釈レイヤー |
|---|---|---|
| 数 | 1つだけ（`selectedId` は単数） | 複数 |
| 明示性 | 暗黙。前のターンの選択が残っていても送られる | 添付したものだけ（R8） |
| 意図 | 無い。本文と対象が1対1でしか対応しない | 対象ごとにラベルが付く |

**拡張に備えてスキーマを一般化する必要はない。** D3で永続化しないと決めたため、後から `target.kind` や発信者の区別を足すコストはゼロで、移行も互換も発生しない。概念として認識しておけば足り、今作るのは矩形とラベルだけでよい。

## 8. 成功条件

**狙った状態に到達するまでの往復回数が、テキストのみの場合より減ること。**

0→1と手直しの両方で測る。減らないなら、人間が注釈を置く手間がそのまま純損失になる。その場合はこの機能を捨てる。
