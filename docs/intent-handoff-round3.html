Weave · Concept Extension · Round 3 · 2026-08-11

渡すときは粗いのに、返ってくるのは完成品。

第1巡と第2巡の候補10件は、すべて画面にすでに何かある状態を前提にしている。直した、選んだ、崩したくない、戻した。第3巡が扱うのはその手前——頭の中の像が、まだ一度も画面に出ていない段階である。

本命は「ラフで話しかけたら、ラフで返る」。 ラフは今、人間→Agentの一方通行の入力形式になっている。同じ記法をAgent→人間にも流すと、二人が同じ面の上で、同じ粗さで考えられるようになる。共同作業を1段階進めるのは新しい入力欄ではなく、この逆流路である。
詰まっている場所 本命の形 返すもの・返さないもの 併走候補 追加の原則 実装順

01 · Gap

詰まっているのは入口ではなく、返り道

0→1でイメージが伝わらないとき、人間はたいてい「うまく説明できなかった」と考える。しかし実際に起きているのは、粗いラフを渡したのに、完成したHTMLが返ってくることである。粗い入力は訂正しやすく、完成品は訂正しにくい。だから最初の1枚が出た瞬間に、会話はチャットの言い直しへ戻る。

頭の中にある像今の入口どこで失われるか
どこに何を置きたいかラフの矩形＋ラベル（実装済み）渡せている
話せば言えるが、書くと死ぬ説明チャットに要約して書く順序・強弱・言い回しが、要約の時点で落ちる
紙やホワイトボードにもう描いた写真を貼って言葉で補う画像は根拠として渡るが、人間が直せる形にならない
全体の流れは見えているが、1枚ずつは決まっていない1枚ずつ作らせて後で並べ替える束としての意図が、枚数の都合で崩れる
出てきたものが違う、と分かるだけ「もう少しこう」と言い直すAgentの理解が見えないので、どこで分岐したか特定できない
どこまで作り込んで見せてほしいか毎回チャットで書き添える骨組みが欲しいのに仕上げが来て、議論が細部へ逃げる

「出てきたものが違う、と分かるだけ」の行を除けば、残りはいずれも入口を足せば埋まるように見える。声を入れる、写真を取り込む、束ねる。しかし入口だけを足すと、返ってくるものは今までどおり完成HTMLのままである。素材を豊かにするほど、外れたときに何がどう伝わったのか分からなくなる。

先に必要なのは、Agentの理解が人間と同じ粗さで見えることだ。注釈レイヤーはすでにその形式を持っている。矩形＋ラベル、1280×720座標、真実に混ぜない下書き（D3）、生成結果の上に重ねる表示（R11）。足りないのは形式ではなく、その形式にAgent側の発信者がいないことだけである。

02 · First feature

読み合わせのラフ — ラフで話しかけたら、ラフで返る

Rule

矩形の注釈を含むターンを送ったときだけ、Agentは最初にラフで返す。

既存要素を @ で指しただけの手直しのターンは、今までどおり即HTMLである。人間が覚える作法はゼロで、粗く話しかけたら粗く返る、という対称性だけがある。

Example · 4 actions

「左に写真、右に3項目」から、最初のHTMLまで。

人間が描くラフモードで矩形を2つ。ラベルは「現場の写真」「Q3の要点 3つ」。チャットは空でよい。
Agentが描き返す完成HTMLの前に、自分が置くつもりの構成を矩形＋ラベルで返す。人間のラフの上に重なって表示され、ずれている場所が目で分かる。
人間が直す言葉で訂正しない。Agentの矩形を動かす、ラベルを書き換える、要らないものを消す。それがそのまま次の入力になる。
作る「これで作る」で同じターンの続きとしてHTMLが出る。訂正が無ければ、そのまま素通りできる。
新しいデータ形式は要らない。

Agentが返すラフは、人間が描くラフと同じ配列・同じ座標系（D4）に入る。追加は発信者を表す1属性だけで、描画は送信済み注釈の重ね表示（R11）をそのまま向きだけ変えて使う。人間はAgentの矩形を、自分の矩形と同じ操作で動かせる。

承認ゲートではない。

ラフはHTMLではないので、真実（slides/*.html）に一切書かない（D3）。止めているものが何も無いため、concept.md 2.1 の無条件上書きは崩れない。素通りもでき、Agentのラフを無視して直接HTMLを書かせることもできる。これは合意の手続きではなく、返り値の粗さの選択である。

粗く返すのは、Agentが分かっていないからではない。

完成品は、合っている部分と外れている部分を同時に運ぶ。人間は外れているところだけを指したいのに、目の前には全部が仕上がった1枚がある。矩形3つなら、外れている1つを掴んで動かせる。訂正のコストは、返ってきたものの解像度で決まる。

03 · Handoff

Agentが返すもの、返さないもの

追加は注釈エンベロープに1属性、shared/context.mjs の contextPromptRules に2文。第2巡の marks と同じ層に並ぶ。

// Agent → 人間。人間が描く注釈と同じ配列・同じ座標系に入る
{
  "annotations": [
    { "author": "agent", "region": { "x": 80, "y": 140, "w": 520, "h": 440 }, "label": "現場の写真" },
    { "author": "agent", "region": { "x": 640, "y": 140, "w": 560, "h": 200 }, "label": "Q3の要点 3つ" }
  ]
}

// contextPromptRules への追記
When the turn contains region annotations, reply first with your intended
layout as regions in the same coordinate space, then wait for the next turn.
Keep it to the fewest regions that show the structure. Do not write HTML yet.

返すもの

  • 構造が分かる最小個数の矩形（目安5つ以内）
  • 各矩形の「何が入るか」だけを書いたラベル
  • 人間のラフとの対応が付かなかった箇所
  • 判断できなかった点があれば短い1文

返さないもの

  • 完成HTMLの下書きやCSS
  • 矩形の中のテキスト本文（それは作る段でよい）
  • 手順の説明（「まずflexで囲んで…」）
  • 人間が描いた矩形の書き換え（動かすのは人間の操作に限る）
  • 保存される記録（ラフは真実に混ざらない・D3）

成功条件。 0→1のターンで、最初のHTMLが出るまでに作り直しが何回起きたかを数える。ラフの読み合わせを1往復挟むことで、HTML生成の回数が減るかどうかがこの機能の全価値である。減らなければ、それは往復を1回増やしただけの手間になる（第1巡の原則06）。

04 · Candidates

併走候補

いずれも「イメージの入口を、人間の外にある素材へ広げる」候補である。番号は第1巡・第2巡から続けている。

10

語りから骨格を起こす — 話したことを、デッキの割りにする

Narration

プレゼンは元々「話す」ものなのに、入口は書くことしかない。話した説明、あるいは書き殴った長文を渡すと、Agentは文章をスライドへ貼るのではなく、フィルムストリップ上の割り——何枚で、各枚が何を担うか——をラフとして返す。人間はその並びを掴んで直す。

拾う思考

順序、強弱、どこで山を作るか。まだ整理されていない全体像。

重要な制約

文章をそのまま箇条書きにしない。それは変換損失を減らすのではなく、資料を文字起こしに変える。

11

持ち込みをラフへ翻訳する — ホワイトボードの写真、手描きのスケッチ

Import

イメージはすでに人間の外にあることが多い。写真や手描きを貼ったとき、返るのは完成HTMLではなくラフである。読み取りを間違えていれば、人間は矩形を動かすだけで直せる。第1巡05「参照レンズ」とは役割が違う。あちらは他人の作ったものから好みの部分を借りる機能で、これは自分がすでに描いた下書きを持ち込む機能である。

拾う思考

会議中に手が先に描いてしまったもの。言葉へ戻す前の構成。

既存資産

本命の逆流路がそのまま使える。翻訳先が同じラフなので、入口が増えても後段は増えない。

12

作り込み度を選ぶ — 骨組みで見せるか、仕上げて見せるか

Fidelity

イメージがまだ揺れている段階で完成品を見せられると、議論は色や余白へ逃げる。出力の粗さをひとつのつまみにする。本命はこの連続量のいちばん粗い端——矩形とラベルだけの位置——に当たり、途中には「見出しと枠だけのHTML」がある。

拾う思考

いま確かめたいのは構成なのか、仕上がりなのか。

重要な制約

つまみを常設のフォームにしない。ラフを含むターンの既定を粗い側に置けば、明示的な操作は要らなくなる。

13

たとえで指す — 「この感じで」をデッキの中から選ぶ

Precedent

人間は前例で語る。「3枚目みたいな作りで」。デッキ内の既存スライドを指すだけなら、実HTMLが手元にあるので変換損失はほぼゼロで、外部画像（第1巡05）より確実に効く。最も安く、最も早く入る候補。

拾う思考

名前を知らないまま見分けている作りの好み。

既存資産

フィルムストリップの選択、@ の指差し語彙（D9）。渡すのはスライドidひとつ。

05 · Guardrails

第1巡の6原則・第2巡の3原則に足す3つ

10

返り値の粗さを、入力の粗さに合わせる

粗く渡したものに完成品で答えると、人間は訂正の足場を失う。返ってきたものの解像度が、そのまま訂正のコストになる。

11

逆流路を先に作る

声・写真・前例といった入口は、返りが完成HTMLのままだと「入れた結果が違う」を訂正できない。入口を増やす前に、返り道を人間の記法に合わせる。

12

Agentの下書きも、真実に混ぜない

Agentが返すラフもHTMLではなく、保存もgitもundoも対象外である（D3）。方向が増えても、真実は slides/*.html の1本に保つ。

06 · Sequence

推奨する実装順

PHASE 1

決まり具合を渡す

第2巡の Firm / Draft。envelopeに1キー、プロンプトに2文。最も小さく、最も早く測れる。

PHASE 2

ラフで返す

本命「読み合わせのラフ」。0→1の往復がここで初めて縮む。新しいUIはほぼ要らず、注釈の描画に発信者を足すだけで通る。

PHASE 3

素材の入口を開く

前例で指す（13）→ 持ち込みの翻訳（11）→ 語りから骨格（10）。返り道が出来ているので、読み取りの外れを人間が直せる。

PHASE 4

面を共有する

第1巡03の問い返し、04の決定の糸、09の関係を引く。指示面が完全に双方向の思考の面になる段階。

判断。 第2巡の Phase 1 を動かしていない。読み合わせのラフを先に置きたくなるが、Firm / Draft のほうが実装が小さく、しかも「読み合わせで確認した部分は崩さない」という次の段の土台になる。順番を入れ替えると、ラフで合意した内容が次のターンで崩れて見える。

根拠: 思考をAgentへ渡す、次の機能（第1巡）、決まり具合を成果物の上に置く（第2巡）、concept.md 1 / 2.1 / 2.5、docs/annotation-layer-design.md D3 / D4 / D9 / D10 / R11。これは機能提案であり、データ形式とAPIの確定仕様ではない。
