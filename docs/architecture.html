Weave · システム構成

ローカルで完結する、HTMLを真実としたスライドエディタ

人間とAgentが同じHTMLプロジェクトを同時に編集する。その要求から決まった構成と、中核で使っている技術を1枚にまとめる。

§1全体像

動いているのは3つのプロセスと、1つのgitリポジトリだけ。クラウド側に状態を持つ場所は無い。

プロセス実体責務
画面 vinext（Vite + React）の開発サーバ、:3000 編集UI。キャンバスはスライドHTMLを実DOMとして注入し、その場で書き換える。状態モデルを別に持たない
ローカルAPI server/local-api.mjs、素のnode HTTP、:4317 プロジェクトファイルの所有、保存トランザクション、git操作、Codexの中継。CORSは localhost:3000 のみ許可
Codex app-server ローカルAPIが codex app-server をspawn Agent本体。stdio越しのJSON-RPCで会話する。認証はCLIの既存ログインをそのまま使う
この形の効き目。OpenAIの資格情報がアプリの中を通らない。ブラウザからapp-serverへの経路が存在しないので、画面に渡す情報を絞る設計判断が要らなくなる。

§2真実の置き場所

中間データモデルを持たない。スライドの真実は slides/<id>.html の <main class="weave-slide"> フラグメントそのもので、エディタはそれをDOMとして描き、DOMを直接編集し、outerHTML に戻して書き出す。

この判断が連鎖して、他の置き場所の役割が決まっている。

  • .weave/deck.json は目次。並び順・名前・スピーカーノートだけを持つ。名前はHTMLのタイトルスロットから導出される表示用の値で、原本ではない
  • styles/deck.css は生成物。内容が正準と一致しなければ保存を弾く（実質read-only）
  • assets/ は内容のsha256をファイル名にする。同じ画像が二重に入らない

結果として、Agentへの指示は「このファイルを編集して」で済む。人間の操作とAgentの操作が、同じ対象への別々の書き込み手段になる。

§3保存とgit

保存はスライド全ファイルと目次の一括更新なので、途中で落ちると「新しいスライドと古い目次」のような中間状態が残りうる。それを作らないために、書き込みは別名で用意してから差し替える方式にしている。

gitは「あとから見るためのログ」ではなく記録システムそのものとして使っている。

  • 履歴 — 保存ごとにWeave名義でコミット。過去のコミットへ戻す操作も、消すのではなく「戻したことをコミットする」
  • 複数提案 — Agentの案は weave/variation/* ブランチ。採用は fast-forward マージ、不採用は weave/history/* へ改名して残す
  • リビジョン競合 — 画面が読んだHEADと保存時のHEADが違えば拒否する。Agentが裏でコミットした変更を人間の保存が踏み潰さない

§4スタイルの単一ソース

スライドの見た目はTailwind標準のユーティリティクラスだけで表現する。ただしTailwindのコンパイラは通らない。使えるクラスの一覧を持つレジストリがコード内に1つあり、そこから生成したCSSをスライドに適用している。

この1箇所が、性質の違う3つの仕事を同時に決めているところが肝。

付随して決まっていること。

  • 固定設計サイズ 1280 × 720。レスポンシブに書かず、表示側で拡大縮小する。だから絶対pxのCSS1枚が編集画面・発表モード・書き出しHTMLすべてに使える
  • インラインstyle属性と任意値クラス（[…]）は禁止。保存時に弾く。値が定義の外に漏れると、上の3者の一致が崩れる
  • prettierを正準フォーマッタにする。人間のDOM由来のHTMLとAgentが手で書いたHTMLを同じ形に揃えるので、gitのdiffが意味を持つ。改行は <br> に統一（prettierがテキストを折り返すため、生の改行は失われる）
  • 書き出しは自己完結HTML。CSSをインライン化し、外部参照を持たない1ファイル

§5型と2つのスロット

2026-08-08に入った層。型（テンプレート）は中身を持たない器で、背景・枠・共通の書式だけを持つ。templates/<id>.html という、スライドと同じ形のHTMLファイル1つで完結する。

<!-- templates/orbit.html — 空の器 -->
<main class="weave-slide … theme-orbit bg-slate-950 text-lg leading-normal"
      data-weave-template="orbit" data-weave-template-name="Orbit / Dark">
  <div class="brand …">WEAVE</div>                        枠（編集対象外）
  <section class="hero flex flex-1 …" data-weave-slot="content">
    <h1 class="heading text-6xl …" data-weave-slot="title"></h1>
  </section>
  <div class="page-number …">01 / 01</div>                枠（位置から採番）
</main>

スロットを「タイトル」「内容」の2つに固定したのが、型を後から変更できる条件になっている。数が可変だと、型を変えたときどの中身をどこへ入れるか決まらない。2つなら タイトル→タイトル、内容→内容 で機械的に決まる。

型の適用は、枠を新しいものに差し替えて2つのスロットの中身を移すだけ。HTML文字列に対する純粋関数なので、ブラウザ無しで検証できる。「新規スライドを作る」は、移す中身が無いだけの同じ操作になる。

共通の書式はCSSの継承で配る。型のルートに置いたクラスを子が継承するので、型を変えれば文字の見た目も変わる。ただし継承できるプロパティに限られ、eyebrowの小ささのような「その種類がそういうものだ」という寸法とアクセント色は明示のまま残す（型はHTML1枚なので、ルートから配れる文字サイズは1つしかない）。

タイトルスロットのテキストはスライドの名前そのもの。以前はインスペクタの名前欄とキャンバスの見出しが無関係で、同じ文字列を2回打つかズレるかのどちらかだった。

§6Agent統合

Codex CLIの app-server を子プロセスとして起動し、stdio越しのJSON-RPCで話す。HTTPでもSDKでもない。

  • 型は生成する — codex app-server generate-ts の出力を generated/codex-app-server/ に置く。生成時のCLI版（現在 0.146.0）を記録し、起動時に実際のCLI版と比較して、食い違えば画面に出す。プロトコルの変化を黙って踏まない
  • イベントは連番付きNDJSON — /api/codex/events?after=N でストリームする。直近2000件をメモリに保持しているので、再接続時に続きから受け取れる
  • 承認要求は逆方向のRPC — コマンド実行やファイル変更の承認、MCPの問い合わせはサーバ→クライアント方向の要求として届く。ローカルAPIがUIに出せるものだけを選んで画面へ渡し、返答を戻す
  • 文脈は自動で渡す — 選択中の要素、直近の履歴などAgentがファイルから得られない視点
  • 作法はAGENTS.mdで伝える — HTMLが真実であること、使えるクラス、スロットの語彙、装飾はinline SVGにすること。プロジェクト内のファイルなので、Agentが普通に読む

§7技術要素

技術版用途選んでいる理由
React19.2 編集UI キャンバスはReactの管理外に置き、実DOMを直接編集する。再レンダリングでキャレットが飛ばないようにするため
vinext / Vite0.0.50 / 8.0 アプリの配信・開発サーバ Next.jsのApp Router互換の構成をVite上で動かす。Cloudflare向けビルドもここに含まれる
Tailwind CSS4.2 エディタ自身の画面 スライド側には使わない。スライドは §4 のレジストリから生成したCSSを使う
node:httpNode 22.13+ ローカルAPI フレームワークを入れていない。ループバック限定・単一利用者で、ルーティングは if の列で足りる
git（CLI）— 履歴・提案・復元 ライブラリを介さず execFileSync で叩く。人間が同じリポジトリを普通のgitとして触れることが要件
Codex app-serverCLI 0.146.0 Agent 公式のライフサイクル（初期化・thread・turn・通知）に沿う。資格情報はCLIに置いたまま
prettier3.9 HTML / CSSの正準化 2人の書き手（人間のDOM出力とAgentの手書き）を同じ形に揃える。gitのdiffを意味あるものにする
TypeScript5.9 画面と生成プロトコル型 サーバ側は .mjs のまま。共有モジュールも .mjs にして、ブラウザとnodeの両方から同じファイルを読む
node:test組込み テスト ランナーを追加しない。94件が数百msで走る

shared/ は拡張子を .mjs に統一している。スライドの移行処理・スロット操作・監査・ユーティリティ定義を、ブラウザとローカルAPIが同一のファイルとして読むため。2つの実装が食い違う余地を作らない。

§8使っていないもの

リポジトリには足場が残っていて、構成を読むときに誤解しやすいので明記する。

  • データベースは無い。db/schema.ts は空で、getDb() を呼ぶ箇所はゼロ。drizzleとD1の設定はスターターテンプレート由来
  • Cloudflare Workerはアプリ配信のみ。worker/index.ts は雛形のままで、Weaveの機能を何も知らない
  • API Routeは無い。app/ に route.ts は存在せず、画面は "use client"。データの出入りは全部 :4317 を通る

つまり npm run dev を落とすとエディタは保存もAgent接続もできない。逆に言えばクラウド側に何も要らず、プロジェクトをgitごと持ち出せば完結する。

§9壊れないための仕掛け

「HTMLが真実」という前提は、放っておくと崩れる種類の約束なので、検査を仕組みに入れている。

  • 内容ポリシー監査 — <script>、インラインイベントハンドラ、javascript: URL、外部URL、インラインstyle、未登録クラス、任意値クラスを保存時に拒否。スライド・型の両方を通す
  • 構成テスト — ソースを文字列として読み、撤去したはずの旧実装が残っていないか、UIの契約（ポップオーバーの閉じ方など）が守られているかを検査する。DOMの無い環境で構成の退行を捉えるため
  • 純粋関数への切り出し — 移行・スロット操作・型の適用はHTML文字列に対する関数にしてある。ブラウザを立てずに往復不変性まで確認できる
  • 往復不変性 — 型AからB、Bから戻したときに元のHTMLに一致すること。編集がファイルを少しずつ汚さないことの担保
