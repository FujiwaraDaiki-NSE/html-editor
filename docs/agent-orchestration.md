# オーケストレーションの要件と実装記録

## 合意した要件

- モデル選択がオーケストレータ選択を兼ねる。Codex／Claudeの別の選択UIは追加しない。モデルを変更したら新しい会話を開始する。
- Claudeは既存のClaude Codeログインを使い、会話の実行経路はCodex app-serverを経由しない。バージョン付きモデル指定を維持する。
- 実装は明示的に選択したCodexモデルへ委任する。オーケストレータは指示、進捗の判断、差分レビュー、結果報告を担当する。
- 作業中もメッセージを送れる。追加指示を受けたオーケストレータが担当単位で継続・変更・停止を判断する。
- 実行方法は「編集を任せる」「確認してから編集」。後者は人間がカードを承認するまで担当を起動しない。両方とも反映前にオーケストレータがレビューする。
- 提案や計画の相談は会話で応答する。提案モードと計画モードは設けない。
- 担当の対象、指示、モデル、試行回数、進行状況、レビュー、作業結果を確認できる。
- 変更範囲、同時編集、復旧、履歴、スキル、探索案などの既存機能を維持する。

## 実装上の境界

`Orchestration`が受信メッセージと担当作業の状態を所有する。モデルの1応答が終わっても担当を停止しない。モデルはツールで作業を依頼し、受付だけを受け取って会話を終了できる。実装結果のレビューが必要になったらアプリから会話へ通知する。

担当のファイル書き込みは1件ずつ行う。会話や追加指示の受付をこのキューで止めない。新しい指示を未判断の待機担当は開始しない。すでに開始した担当への変更は停止・復旧後に新しい指示で再実行する。完了済みの作業を取り消したことにはしない。

人間の指示ごとにバージョンを増やす。レビューには同じバージョンの変更前後の閲覧を必要とし、反映時のプロジェクトロック内でも再検査する。大きなソースはページ分割し、全ページ閲覧前のレビューを拒否する。人間の追加指示の記録、承認、中止、反映を同じプロジェクトの排他処理で順序付ける。

Claudeへは読み取り専用ファイルツールと専用MCPだけを提供する。MCPトークンは会話・ターンに限定し終了時に破棄する。人間用の承認ボタンはAgent UI操作から除外する。ブラウザーのセッション所有権も検証する。

プロジェクト作成・切り替えがAgentの画面操作として完了した場合のみ、認証済みブラウザーの新しい編集コンテキストを会話へ引き継ぐ。作業の対象ルートは作成後に変更しない。

状態ファイルへブラウザーの認証トークンを保存しない。起動時に未完了担当と未配信受付を失敗として記録し、自動で再送・再実装しない。Codexの追加指示の配信確認が不明な場合も再送せず表示する。

## 確認

- 自動テスト：委任の非同期受付、受信IDの重複排除、Codexの追加指示、Claudeの応答中断と担当継続、人間承認前の起動禁止、古いレビューの拒否、反映直前の指示変更、順次書き込み、中止、再起動時の再送禁止、ソースページ分割、既存会話のツール移行。
- 実機：Claude Opus 5.5 → GPT-6.1-Sol、確認モード、承認後の担当起動、実装中の追加指示、Claudeのレビュー、指定した見出しだけの反映。
- 実機：GPT-6.1-Sol → 別のGPT-6.1-Sol担当、編集を任せるモード、オーケストレータの差分レビュー、指定した見出しだけの反映。
- 実機確認には専用ポートと一時workspaceを使用し、ユーザーの資料を編集しない。
